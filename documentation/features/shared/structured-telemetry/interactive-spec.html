Objective

Define a complete, privacy-safe telemetry contract for the Shifu Web/BFF and API services. Every operational log is one structured JSON line suitable for CloudWatch ECS collection, with bounded correlation across HTTP requests, jobs and integrations. This is infrastructure-only and changes no product outcomes, permissions, persistence models or user journeys.

Complete mode is required because the contract crosses applications, middleware, jobs, providers, security/privacy controls and staging verification.

No canonical module RP/JN applies. Requirements trace to Jira SHIFU-94 and the canonical privacy policy's technical-log rules; no product IDs are invented. No .rest collection is created because this change adds no REST resource or route contract.

Required level/event values are validated at the typed boundary; invalid required values are dropped defensively. Unknown keys and invalid optional operation, job, integration or dependency values are omitted while a valid event remains emit-able; callers cannot provide the derived message or provider envelope fields.

Behavior Contract

Functional requirements RF-01—RF-08
  1. RF-01. One JSON line per Web/BFF and API event with UTC timestamp, level, service, environment, version, event and safe message.
  2. RF-02. Use X-Request-ID; retain valid UUID v4, replace invalid/missing values, echo responses and forward BFF→API.
  3. RF-03. Jobs/integrations use bounded run_id/event_id with operation, result, duration and retry fields when applicable.
  4. RF-04. Allowlisted technical fields only; exclude credentials, bodies, content, IPs, user agents and user/account identifiers.
  5. RF-05. Unexpected errors contain stable code, exception type and sanitized frames, never raw messages; telemetry failure never changes business results.
  6. RF-06. Explicit environment/log-level/release-version configuration; local INFO default and deployment-controlled temporary DEBUG.
  7. RF-07. Catalog HTTP, errors, auth, goal/attempt/evaluation, jobs, integrations, lifecycle and dependency events.
  8. RF-08. Staging proves parsing, correlation, version and privacy in both CloudWatch groups with 14-day retention.
Acceptance criteria CA-01—CA-07
  1. CA-01. Every emitted line parses and contains mandatory fields at the configured level/version. RF-01/RF-06; CI-01/CI-02.
  2. CA-02. Missing, malformed and valid request IDs behave consistently across BFF, API and response headers. RF-02; CI-03/VM-01.
  3. CA-03. Job/integration lifecycle events contain only applicable correlation and safe operation fields. RF-03; CI-04/VM-02.
  4. CA-04. Forbidden fields and values never appear in serialized telemetry. RF-04; CI-01/CI-05/VM-03.
  5. CA-05. Sanitized unexpected errors preserve the original product response/result. RF-05; CI-05/VM-03.
  6. CA-06. Staging CloudWatch queries prove both groups, correlation/version, privacy and exactly 14-day retention. RF-07/RF-08; CI-07/VM-04.
  7. CA-07. Every Auth/Learning owner emits its fixed matrix event exactly once after the terminal outcome; retry dispatch emits no false evaluation completion and business identifiers are absent. RF-07; CI-08/VM-02.

The active TanStack request context is passed through next({context}); each server function passes the typed requestId to the server-only REST factory. The shared Axios utility accepts only an optional header and never uses global mutable state or AsyncLocalStorage. The provider derives the catalog message and injects timestamp/service/environment/version.

Fixed event catalog and sanitization

Events are http.request.completed, http.request.failed, error.unexpected, auth.login.succeeded, auth.login.refused, auth.session.revoked, auth.access.denied, learning.goal.created, learning.goal.deleted, learning.attempt.submitted, learning.evaluation.completed, job.started, job.completed, job.failed, job.retrying, integration.operation.started, integration.operation.completed, integration.operation.failed, integration.operation.retrying, app.startup.completed, app.shutdown.completed, app.version.reported and dependency.unavailable. Jobs use stable registered <module>.<job_name> identifiers; all 15 current registrars are covered by the shared wrapper. Resend is proven through identity/communication consumers and OpenRouter/Jev through intelligence/learning consumers. error_code is lower-snake-case, at most 80 characters and drawn from invalid_credentials, identity_unavailable, service_unavailable, invalid_input, bad_request, unauthorized, forbidden, not_found, conflict, method_not_allowed, content_too_large, unsupported_media_type, validation_error, rate_limited, request_failed, internal_error, job_failed, integration_unavailable and integration_failed; raw exception/provider text is never copied. run_id/event_id are limited to 128 safe ASCII characters; invalid values are omitted. Routes are templates or unmatched, never raw paths. Integrations are Inngest, Resend and OpenRouter. Stack traces contain at most 20 basename-only frames with optional positive line/function fields and no source snippets or raw messages.

Runtime flow and guarantees

The middleware validates or generates a request ID, passes typed context through the BFF and forwards it across the existing BFF→API call. HTTP boundaries emit safe timing/status events. Jobs and integrations emit run/event correlation at their consuming boundaries. FastAPI/Uvicorn owns startup/shutdown; Web reports version once on the first server-side request. Error handlers extract stable codes and sanitized frames. Serialization is best effort and cannot alter business outcomes. There is no universal correlation ID, persistence migration, browser analytics or event-contract change.

Verification Contract

This draft contract specifies required proof; it contains no implementation evidence.

Integration operation values are inngest.dispatch, resend.send and openrouter.generate; result and error_code describe their outcomes. Error codes are lower-snake-case, at most 80 characters and drawn from the fixed safe catalog; raw exception/provider text is never copied.
